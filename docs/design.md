# طراحی: یک لایهٔ حافظهٔ مستقل از ایجنت (`mem`)

> ورودی: `research.md` (رفتار واقعی Claude Code و Qoder).
>
> **اصل حاکم:** هرچه در آن دو هست برمی‌داریم، هرچه نیست نمی‌سازیم؛ تنها افزودهٔ ما «مشترک بودن
> بین ایجنت‌ها» است — یک انبار، یک سرور MCP، نه یک پلاگین برای هر ایجنت.
>
> **وضعیت:** پیاده‌شده (نسخهٔ `0.2.0`). این سند طرحِ فعلی است؛ اگر جایی با کد اختلاف داشت،
> `README.md` مرجع است. نسخه‌های حذف‌شده (بازیابی لغوی، هوک‌ها، تاریخچهٔ git، استخراج) عمداً
> همین‌جا ثبت شده‌اند تا دوباره پیشنهاد نشوند.

---

## ۱. فرض‌ها

- یک ایجنت در هر لحظه، گاهی دو. نوشتن هم‌زمان نادر است؛ `if_version` محافظ اصلی است و
  `write`/`delete` برای همان بررسی یک قفل کوتاه‌عمر روی inode پوشه می‌گیرند — بدون فایل و
  بدون state، که با مرگ پروسه آزاد می‌شود.
- حجم: ده‌ها تا چند صد یادداشت، نه هزاران. اسکن پوشه ارزان است؛ بدون دیتابیس و بدون ایندکس
  جست‌وجو.
- داده باید با `cat` و `grep` خوانا بماند؛ هیچ فرمت اختصاصی‌ای وجود ندارد.

## ۲. چه چیزی از آن‌ها گرفته‌ایم

| رفتار | از کجا | چرا |
|---|---|---|
| `MEMORY.md` به‌عنوان فهرست یک‌خطی | هر دو | ارزان، خوانا، قابل grep |
| یک فایل markdown به‌ازای هر یادداشت با `name`/`description`/`type` | هر دو | همان شکلی که ابزار خودشان می‌خواند |
| چهار نوع `user`، `feedback`، `project`، `reference` | هر دو | تاکسونومی آزموده‌شده |
| «چه وقت ذخیره کن» به‌ازای هر نوع، و تفکیک حافظه از plan/task | دستورالعمل خود Claude Code | همان چیزی که کیفیت نوشتن را تعیین می‌کند، نه قالب |
| نسخه‌بندی خوش‌بینانه (`if_version`) | Claude Code | جلوی بازنویسی کور را می‌گیرد |
| نوشتن دو مرحله‌ای: سند، بعد خط فهرست | هر دو | بدون خط فهرست، یادداشت مرده می‌سازی |
| دو scope: `global` و `project` | Qoder | ترجیح شخصی باید در همهٔ پروژه‌ها باشد |
| تثبیت (ادغام تکرار و جایگزینی نسخهٔ کهنه) | `autoDream` در Claude Code | جلوی پوسیدگی حافظه را می‌گیرد |

## ۳. چه چیزی را عمداً کنار گذاشته‌ایم

| کنارگذاشته | چرا |
|---|---|
| سقف ۲۰۰ خط / ۲۵KB روی فهرست | فهرست تنها راه بازیابی است؛ بریدنش یادداشت را پنهان می‌کند، نه context را کم |
| بازیابی لغوی و آستانهٔ انتخاب | فهرست کامل و خواندن on-demand کافی است؛ هم‌پوشانی واژه‌ای بدون مدل «مرتبط بودن» را نمی‌فهمد و بیشتر تکرار فهرست می‌شود |
| استخراج پس‌زمینه از transcript | نه Claude Code و نه Qoder چنین پاسی نداشتند که خواسته باشیم؛ خودِ ایجنت می‌نویسد |
| هوک/پلاگین مخصوص هر ایجنت | MCP برای هر ایجنتی که کلاینت MCP دارد کافی است؛ یک آداپتور، نه چهار |
| بخشی در `AGENTS.md` برای معرفی سیستم | `instructions` خود MCP این کار را می‌کند و همراه سرور سفر می‌کند |
| تاریخچهٔ git در انبار | Claude Code هم rollback نداشت؛ تثبیت فقط با تطبیق نسخه حذف می‌کند و تاریخچه لازم نیست |
| `.state/`، شمارش سشن، `dream.log` | تثبیت بعد از هر تغییر اجرا می‌شود؛ استیتی نمی‌ماند که بخواهد شمارش شود (قفل، اگر هست، فقط یک `flock` کوتاه‌عمر روی inode پوشه است، نه فایل state) |
| `config.toml` | هیچ تنظیمی نمانده که فایل بتواند بگوید؛ `MEM_ROOT` و `MEMORY_PROJECT_CWD` تنها ورودی‌ها هستند |
| فیلدهای `confidence`، `tags`، `supersedes`، `id` و مانند آن | Claude Code هم ندارد؛ `modified` کار را راه می‌اندازد |
| صف `candidate`/`review`، SQLite، امتیازدهی، tombstone | برای این حجم و این مدل کار، پیچیدگی بی‌بازده |

**تاریخچه:** P0–P2 نسخهٔ اول این‌ها را داشت (بازیابی لغوی با آستانه، هوک‌های `SessionStart` و
`UserPromptSubmit`، پلاگین opencode و DSH، استخراج پایان سشن، تاریخچهٔ git). در بازبینی
۲۰۲۶-۱۰-۲۸ همه حذف شدند چون هر کدام یک جزء متحرک اضافه می‌کردند بدون آن‌که بازیابی یا نوشتن
را بهتر کنند.

## ۴. معماری

```
   Claude Code          opencode             DSH
   (MCP client)        (MCP client)      (mcp-client)
        └───────────────────┼───────────────────┘
                            │  stdio, JSON-RPC
                   ┌────────▼────────┐
                   │   mem mcp       │   ← تنها رابطِ ایجنت‌ها
                   │ index · read    │
                   │ write · dream   │
                   └────────┬────────┘
                            │
                   ┌────────▼─────────────────┐
                   │  ~/.agents/memory/       │
                   │  markdown، بدون state    │
                   └──────────────────────────┘
```

`mem` (همان پکیج) تنها جای منطق است. CLI برای انسان و اسکریپت است، نه آداپتور. `PROTOCOL.md`
قرارداد مکتوب برای ایجنتی است که کلاینت MCP ندارد و باید دستی وصل شود.

## ۵. انبار

```
~/.agents/memory/
├── PROTOCOL.md              ← قرارداد برای اتصال دستی
├── global/
│   ├── MEMORY.md
│   └── *.md
└── projects/
    └── -home-mahdi-workspace-foo/   ← همان sanitized-cwd که Claude Code/Qoder می‌سازند
        ├── MEMORY.md
        └── *.md
```

قالب یادداشت، دقیقاً همان قالب Claude Code:

```yaml
---
name: pnpm-not-npm
description: "the lockfile is pnpm; npm install rewrites it and breaks CI"
metadata:
  node_type: memory
  type: project            # user | feedback | project | reference
  originSessionId: 507e6cf4-...
  modified: 2026-10-02T11:20:00.000Z
---

بدنه: چه چیزی، **چرا**، و **چطور اعمال شود**.
```

قالب فهرست:

```markdown
- [Use pnpm, not npm](pnpm-not-npm.md) — the lockfile is pnpm; npm install rewrites it and breaks CI
```

## ۶. خواندن

تنها یک مسیر: **فهرست کامل، بعد خواندن بدنه.**

1. `memory_index` متن `MEMORY.md` هر دو scope را برمی‌گرداند — بدون سقف خط، تا هیچ یادداشتی
   پنهان نماند.
2. ایجنت خطی را که به کارش می‌خورد انتخاب می‌کند و با `memory_read` بدنه را می‌گیرد.

هیچ جست‌وجوی لغوی، هیچ انتخاب‌گر مدل‌محور، و هیچ تزریق خودکاری وجود ندارد. هزینهٔ فهرست
یک‌بار پرداخت می‌شود و بدنه‌ها فقط وقتی هزینه می‌دهند که لازم باشند.

## ۷. نوشتن

| ابزار | پارامترها | رفتار |
|---|---|---|
| `memory_index` | `cwd?` | فهرست هر دو scope |
| `memory_read` | `store`, `path`, `cwd?` | محتوا + `version` + `modified` |
| `memory_write` | `store`, `path`, `content`, `if_version`, `name?`, `description?`, `type?`, `cwd?` | جایگزینی بدنه؛ فیلدهای نیامده حفظ می‌شوند؛ بعد از نوشتن، همان scope تثبیت می‌شود |

قواعد:

- **یک فرمان، هر دو کار**: نوشتن فایل و بازسازی فهرست، و سپس تثبیت scope — همه پیش از بازگشت.
  چیزی برای پاس بعدی باقی نمی‌ماند.
- **`if_version` اجباری** است (`new` برای فایل تازه)؛ نسخهٔ کهنه رد می‌شود و محتوای فعلی
  برمی‌گردد تا ادغام شود.
- **`name`/`description`/`type` اختیاری‌اند**: هر کدام نیاید، مقدار فعلی همان فایل می‌ماند؛ پس
  اصلاح یک غلط تایپی در بدنه، یادداشت را از نوع `user` به `project` نمی‌برد. `description`
  خالیِ صریح، توضیح را پاک می‌کند.
- **رد راز** پیش از نوشتن؛ سقف ۱۰۰KB؛ نام فایل تخت و اجباری `.md`.
- حذف فقط در CLI است (`mem forget`)؛ ابزارهای MCP حذف ندارند.

## ۸. تثبیت (dream)

- **محرک**: هر تغییر (`mem write`، `mem forget`، `memory_write`) scope خودش را تثبیت می‌کند.
  `mem dream` برای اجرای دستی است و `--all` همهٔ پروژه‌ها را می‌گردد. هیچ زمان‌بندی و شمارش
  سشنی در کار نیست.
- **قواعد**: دو فایل هم‌`type` با `name` یکسان = یک یادداشت، جدیدتر برنده و قدیمی حذف؛ دو فایل
  هم‌`type` با هم‌پوشانی توصیف ≥۰٫۸ ادغام می‌شوند (خطوط یکتای قدیمی به جدیدترین می‌چسبد)؛
  `MEMORY.md` بازسازی می‌شود.
- **ایمنی**: حذف فقط وقتی انجام می‌شود که بایت‌های فایل همان باشد که پاس خوانده؛ نوشتن نسخهٔ
  keeper با `if_version`. خودِ پاس قفل نمی‌گیرد — هر حذف و نوشتن نسخه را دوباره بررسی می‌کند؛
  `store.write`/`store.delete` که پیش از پاس اجرا می‌شوند، قفل کوتاه‌عمر پوشه را می‌گیرند.
- **قطعی و idempotent**: بدون فراخوانی مدل؛ اجرای دوم هیچ تغییری نمی‌دهد.
- **محدودیت صادقانه**: تغییرِ نام + تناقض تشخیص داده نمی‌شود. حدس‌زدنش از متن بدون مدل، همان
  چیزی است که نیمهٔ اشتباه یک جفت را بی‌صدا پاک می‌کند.

## ۹. ادغام با ایجنت‌ها

| ایجنت | چطور |
|---|---|
| **Claude Code** | ثبت سرور MCP + `autoMemoryEnabled: false` در `~/.claude/settings.json` |
| **opencode** | ثبت سرور MCP در `~/.config/opencode/opencode.json` |
| **DSH** | یک ردیف `@deepseek-ai/dsh-mcp-client` در `~/.dsh/cordis.patch.yml` |
| **هر ایجنت دیگر** | MCP اگر دارد؛ وگرنه `PROTOCOL.md` را دستی به آن بده |

**چرا `AGENTS.md` نه:** آن فایل در هر سشن کامل خوانده می‌شود و باید کوتاه بماند. `instructions`
خود MCP همان راهنمایی را همراه سرور می‌آورد و بین ایجنت‌ها تکرار نمی‌شود.

**چرا پلاگین/هوک اختصاصی نه:** تنها کاری که آن‌ها می‌کردند تزریق فهرست در شروع سشن و بازیابی
در هر پرسش بود؛ با حذف بازیابی و با `instructions` استاندارد MCP، هر دو کار از خودِ سرور برمی‌آید.

### چرا پل symlink کنار گذاشته شد

ایده این بود که پوشهٔ حافظهٔ بومی Claude Code به انبار ما symlink شود تا ابزار بومی‌اش مستقیم
در آن بنویسد. کنار گذاشته شد چون (۱) قرار نیست در حافظهٔ پیش‌فرض آن دست ببریم، و (۲) باندل
`2.1.301` مسیرهایی را که با symlink بیرون می‌زنند صریحاً رد می‌کند
(`Key escapes personal memory directory via symlink:`).

## ۱۰. حالت‌های خرابی

| حالت | پاسخ |
|---|---|
| خط فهرست جا می‌افتد | هر نوشتن فهرست را بازسازی می‌کند؛ `mem dream` هم |
| دو سشن هم‌زمان یک فایل | `if_version` نوشتن دوم را رد می‌کند و محتوای فعلی را می‌دهد |
| یادداشت کهنه | تثبیت نسخهٔ جدیدتر را جایگزین می‌کند |
| تکرار | تثبیت ادغام می‌کند |
| نشت راز | بررسی پیش از نوشتن |
| تورم context | فهرست یک‌خطی + خواندن بدنه فقط وقتی لازم است |
| حافظه به‌عنوان دستور اجرا شود | `instructions` و `PROTOCOL.md` صریح می‌گویند «reference، نه instruction» |
| حافظهٔ بومی ایجنت هم‌زمان بنویسد | `autoMemoryEnabled: false` |

## ۱۱. تصمیم‌های بسته (بدون دلیل تازه باز نشوند)

- بدون بازیابی لغوی و بدون آستانه؛ فهرست تنها راه است.
- بدون سقف خط روی فهرست.
- بدون تاریخچهٔ git، بدون `.state/`، بدون `dream.log` (قفل فقط یک `flock` کوتاه‌عمر روی inode
  پوشه است، نه فایل state).
- بدون استخراج خودکار؛ ایجنت با `memory_write` می‌نویسد.
- تک‌آداپتور: MCP. بدون هوک و پلاگین اختصاصی.
- بدون فایل تنظیمات؛ `MEM_ROOT` و `MEMORY_PROJECT_CWD` تنها ورودی‌ها هستند.
- بازنویسی فقط فیلدهایی را عوض می‌کند که فراخوان می‌فرستد: `name`، `description` و `type` اگر
  نیایند، مقدار فعلی فایل را نگه می‌دارند (فایل تازه: نامِ فایل، رشتهٔ خالی، `project`). کلیدهای
  فرانت‌مترِ دیگر، مثل `title` دست‌نویس، در بازنویسی دور ریخته می‌شوند؛ تصمیم گرفته شد که فایل
  فقط سه کلیدِ تحت مدیریت را نگه دارد و `title` نمایشی از `name` ساخته شود. `description`
  رشتهٔ خالی صریح، توضیح را پاک می‌کند؛ `name` خالی به مقدار فعلی (یا نام فایل) برمی‌گردد.

## ۱۲. تصمیم‌های باز

1. آیا انبار روی remote هم نگه داشته شود (پشتیبان/اشتراک تیمی)، یا فقط همین ماشین؟
2. اگر روزی کلاینت MCP یک ایجنت از `instructions` استفاده نکرد، آیا `PROTOCOL.md` را باید
   خودکار در فهرست ابزارها نشان داد؟
