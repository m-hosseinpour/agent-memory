# طراحی: یک لایهٔ حافظهٔ مستقل از ایجنت (`mem`)

> ورودی: `research.md`.
>
> **اصل حاکم:** هرچه در Claude Code و Qoder هست، همان را برمی‌داریم؛ هرچه نیست، نمی‌سازیم. تنها چیزی که اضافه می‌کنیم خودِ «مشترک بودن» است.
>
> **وضعیت:** این سند طرحِ پیش از پیاده‌سازی است. سه فاز P0–P2 پیاده شده‌اند؛ هر جا کد با این طرح فرق دارد (مثلاً قفل `dream` یک `flock` است نه pid، و «مدل استخراج» هنوز انتخاب نشده)، مستندِ پیاده‌سازی — `README.md` و `HANDOFF.md` — مرجع است.؛ با یک تفاوت مهم: **بخش ۸ (استخراج پایان سشن) حذف شد** — نه Claude Code و نه Qoder چنین پاسی نداشتند و خواسته هم نشد؛ فقط `dream` مانده است.

---

## ۱. فرض‌های واقعی

- **یک ایجنت در هر لحظه، گاهی دو.** پس نوشتن هم‌زمان نادر است و صف، بافر و قفل سراسری لازم نیست.
- هر ایجنت پوشهٔ حافظهٔ خودش را دارد؛ حافظه بین‌شان جابه‌جا نمی‌شود.
- حجم مورد انتظار: ده‌ها تا چند صد حافظه، نه هزاران.

این سه فرض طراحی را کوچک می‌کند: بدون دیتابیس، بدون صف بازبینی، بدون لایهٔ «نامزد».

## ۲. چه چیزی را از آن‌ها برمی‌داریم (و از کجا)

| رفتار | از کجا | چرا |
|---|---|---|
| `MEMORY.md` به‌عنوان ایندکس یک‌خطی | هر دو | ارزان، خوانا، قابل grep |
| یک فایل markdown به‌ازای هر حافظه، با فرانت‌متر `name`/`description`/`type` | هر دو | همان چیزی که انتخاب‌گر و بازیابی به آن نیاز دارند |
| چهار نوع: `user`، `feedback`، `project`، `reference` | هر دو | تاکسونومی آزموده‌شده؛ چیز جدیدی لازم نیست |
| سقف ۲۰۰ خط / ۲۵KB برای ایندکس | هر دو | تعادل هزینهٔ توکن و دسترس‌پذیری |
| نوشتن دو مرحله‌ای: سند، بعد خط ایندکس | هر دو | بدون خط ایندکس، حافظهٔ مرده می‌سازی |
| نسخه‌بندی خوش‌بینانه (`if_version`) | Claude Code | جلوی بازنویسی کور را می‌گیرد؛ چند خط کد |
| انتخاب حافظه با `name`+`description` در زمان پرسش | Claude Code | تنها مکانیزم بازیابی‌ای که آن‌ها دارند |
| استخراج در پایان سشن | هر دو | چیزی که خودت فراموش می‌کنی یادداشت شود |
| تثبیت دوره‌ای با شمارش سشن | Claude Code (`autoDream`) | جلوی تکرار و تناقض را می‌گیرد |
| دو scope: global و project | Qoder | ترجیح شخصی باید در همهٔ پروژه‌ها باشد |

## ۳. چه چیزی را اضافه نمی‌کنیم

این‌ها در نسخهٔ اول طراحی بودند و حذف می‌شوند:

| حذف‌شده | چرا |
|---|---|
| صف `candidate` / `inbox` / `mem review` | فقط برای حجم بالای استخراج بدون نظارت لازم بود؛ با یک ایجنت، خودِ مدل تصمیم می‌گیرد — مثل Claude Code |
| ایندکس SQLite/FTS5 | ایندکس ۲۰۰ خطی + خواندن فایل با ابزار معمولی کافی است |
| امتیازدهی پنج‌عاملی (recency/type/scope/usage) | انتخاب با مدل روی `description` انجام می‌شود، همان‌طور که آن‌ها |
| `CORE.md` به‌عنوان لایهٔ جدا | لایهٔ همیشه‌حاضر همان `MEMORY.md` است |
| فیلدهای `confidence`، `owner`، `review_after`، `tags`، `sources`، `supersedes`، `pinned`، `id` | کلاد کد هیچ‌کدام را ندارد و با `modified` + تاریخ git کارش را راه می‌اندازد |
| TTL و پیرایش خودکار | بدون `review_after`، تثبیت خودش کهنه‌ها را می‌بیند |
| tombstone برای فراموشی | حذف فایل + خط ایندکس، مثل رفتار آن‌ها؛ تاریخچه در git می‌ماند |
| `mem eval`، `mem stats`، `mem doctor`، `injections.jsonl`، `mem why` | ابزار سنجش، کار فاز بعد است نه بخشی از سیستم |
| قفل فایل و «نویسندهٔ واحد» | دو ایجنت هم‌زمان به‌ندرت پیش می‌آید؛ `if_version` کافی است |

├── PROTOCOL.md              ← قرارداد ۱۵ خطی (به AGENTS.md ارجاع داده می‌شود)
├── global/
│   ├── MEMORY.md
│   └── *.md
├── projects/

## ۶. خواندن

سه گام، هیچ‌کدام LLM اجباری ندارد:

1. **شروع سشن** — `global/MEMORY.md` و `MEMORY.md` پروژهٔ جاری تزریق می‌شوند (سقف ۲۰۰ خط / ۲۵KB هر کدام). این لایهٔ همیشه‌حاضر است و در عمل همان کاری است که Claude Code می‌کند.
2. **به‌ازای پرسش** — اگر تعداد حافظه‌ها از آستانه (`select_threshold`، پیش‌فرض ۴۰) گذشت، یک فراخوانی کوچک فقط `name`+`description` را می‌بیند و مرتبط‌ها را برمی‌گرداند؛ خروجی چند خط ارجاع است، نه بدنه. زیر آستانه هیچ فراخوانی‌ای نمی‌شود، چون ایندکس خودش کوچک است.
3. **خواندن بدنه** — ایجنت با ابزار `Read` خودش فایل انتخاب‌شده را می‌خواند. محتوا فقط وقتی هزینه می‌دهد که لازم است.

اگر چیزی مرتبط نبود، هیچ تزریقی نمی‌شود.

## ۷. نوشتن

دو ابزار مدل‌رو، هم‌نام و هم‌شکل Claude Code:

| ابزار | پارامترها | رفتار |
|---|---|---|
| `memory_read` | `store`, `path` | محتوا + `version` + `modified` |
| `memory_write` | `store`, `path`, `content`, `if_version` | جایگزینی کامل سند؛ `if_version` اجباری (`new` برای فایل تازه) |

قواعد:

- **دو مرحله در یک فرمان**: `memory_write` سند را می‌نویسد **و** خط ایندکس را در `MEMORY.md` اضافه/به‌روز می‌کند. اگر فایل rename شود، خط قدیمی حذف می‌شود.
- **`if_version`**: اگر محتوا از زمان خواندن عوض شده باشد، نوشتن رد می‌شود و محتوای فعلی برمی‌گردد تا ادغام کنی.
- **رد راز**: محتوای حاوی کلید/توکن نوشته نمی‌شود.
- **سقف**: ۱۰۰KB برای هر سند.

نوشتن **مستقیم در مجموعهٔ فعال** است — بدون صف، بدون تأیید. مثل هر دو سیستم.

## ۸. استخراج پایان سشن

یک پاس اختیاری: در پایان سشن، یک فراخوانی کوچک نوار مکالمه را می‌بیند و **فقط اگر چیز بادوامی هست** با همان `memory_write` می‌نویسد.

معیارها عیناً از آن‌ها:

- ذخیره کن: ترجیحات و تصحیح‌های کاربر، تصمیم‌ها و دلیلشان، واقعیت محیطی که از کد درنمی‌آید.
- ذخیره نکن: هر چیزی که از کد/گیت استنتاج می‌شود، کار جاری و موقت، و آنچه `AGENTS.md`/`CLAUDE.md` قبلاً گفته.
- خروجی خالی مجاز و رایج است.

اجرا پس‌زمینه با تایم‌اوت ۲۰ ثانیه و شکست بی‌صدا؛ پایان سشن بلاک نمی‌شود. پیش‌فرض خاموش است تا وقتی مدل را در `config.toml` بگذاری.

## ۹. تثبیت (dream)

همان ایدهٔ `autoDream`، با همان محرک:

- **محرک**: شمارش سشن. `.state/state.json` در هر `SessionStart` یکی اضافه می‌شود؛ وقتی به `every_sessions` (پیش‌فرض ۵) رسید، dream در پس‌زمینه اجرا می‌شود. `mem dream` هم دستی اجرا می‌شود.
- **قفل**: یک فایل قفل با pid؛ اگر اجرای دیگری در جریان است، رد شو.
- **کار**: یک پاس روی حافظه‌های scope که تکرارها را ادغام می‌کند، حافظهٔ متناقض را با نسخهٔ جدیدتر جایگزین می‌کند، و خطوط مردهٔ ایندکس (فایلی که نیست) را پاک می‌کند.
- **ثبت**: یک خط در `dream.log`؛ کامیت git قبل و بعد.

تفاوت صادقانه با `autoDream`: آن سشن‌های اخیر را هم مرور می‌کند؛ ما فعلاً فقط حافظه‌ها را — خواندن transcript چهار ایجنت مختلف کار جداگانه‌ای است و در نسخهٔ اول نمی‌گنجد.

## ۱۰. ادغام با ایجنت‌ها

| ایجنت | تزریق | ثبت | ابزار |
|---|---|---|---|
| **DSH** | پلاگین: `systemPrompt.section()` (ایندکس) + `agent/pre-step` (انتخاب) | `agent/turn-stopping` → `mem extract` | `tools.register` یا MCP |
| **Claude Code** | هوک `SessionStart` و `UserPromptSubmit` با `additionalContext` | هوک `Stop` → `mem extract` | MCP + `autoMemoryEnabled: false` |
| **Qoder** | همان قرارداد هوک (به شکل Codex) | همان | MCP |
| **opencode** | `instructions[]` + هوک `experimental.session.compacting` | هوک `event` روی `session.idle` | MCP |
| **هر ایجنت دیگر** | `PROTOCOL.md` در فایل دستورالعمل | `mem write` | MCP اگر دارد |

`mem hook <event>` JSON روی stdin می‌گیرد و `{"hookSpecificOutput":{"hookEventName":"…","additionalContext":"…"}}` روی stdout می‌دهد؛ سقف ۱۰٬۰۰۰ کاراکتر و تایم‌اوت ۳۰ ثانیهٔ `UserPromptSubmit` رعایت می‌شود.

**محدودیت واقعی opencode:** کانال تزریق در شروع سشن ندارد. پس متن ثابت از `instructions[]`، بازیابی با ابزار MCP، و تداوم با هوک فشرده‌سازی. روی «تزریق خودکار هر پرسش» در آن حساب نمی‌کنیم.

## ۱۱. چرا پل symlink را کنار گذاشتیم

در نسخهٔ اول، ایده این بود که چون قالب ما همان قالب Claude Code است، پوشهٔ حافظهٔ بومی‌اش را symlink کنیم به انبار ما تا `MemoryWrite` بومی مستقیماً در آن بنویسد. **این کنار گذاشته شد، به دو دلیل:**

1. **الزام کار:** قرار نیست در حافظهٔ پیش‌فرض Claude Code دست ببریم. سیستم جدید کنارش می‌نشیند، نه به‌جایش.
2. **ریسک فنی:** در باندل `2.1.301` خطای صریح `Key escapes personal memory directory via symlink:` وجود دارد؛ یعنی backend مسیرهایی که با symlink بیرون بزنند را رد می‌کند. این پل ممکن بود هیچ‌وقت کار نکند.

### کاری که به‌جایش می‌کنیم

Claude Code سه چیز دارد و هر سه استفاده می‌شوند، بدون آنکه به حافظهٔ خودش دست بزنیم:

```json
// ~/.claude/settings.json
{
  "autoMemoryEnabled": false
}
```

کلید رسمی است و توضیح خودش این است: «When false, Claude will not read from or write to the auto-memory directory.» با این، حافظهٔ بومی و `autoDream` بی‌اثر می‌شوند و دو انبار موازی نداریم.

بعد، سه چیز سیستم ما را وصل می‌کند:

- **دسترسی ابزار**: سرور MCP (`mem mcp`) با `memory_read`، `memory_write`، `memory_search`.
- **تزریق**: هوک‌های `SessionStart` و `UserPromptSubmit`.
- **جهت‌دهی**: چند خط در `~/.agents/AGENTS.md` (که `~/.claude/CLAUDE.md` از قبل با `@` واردش می‌کند).

> **نکتهٔ مهم:** متن `CLAUDE.md` یک دستورالعمل نرم است — مدل را هدایت می‌کند ولی ابزار را از دستش نمی‌گیرد. اگر فقط بنویسیم «از حافظهٔ خودت استفاده نکن»، ممکن است باز هم بنویسد. خاموش‌کردن واقعی با `autoMemoryEnabled: false` است؛ متن، مکمل آن است نه جایگزینش.

### گزینه‌ای که استفاده نکردیم

`autoMemoryDirectory` هم کلید رسمی است و می‌شود مسیر حافظهٔ بومی را به انبار ما برد. ولی در `projectSettings` به دلایل امنیتی نادیده گرفته می‌شود؛ پس فقط می‌شود یک مسیر سراسری داد، که با scope پروژه‌ای ما جور درنمی‌آید. برای همین انتخاب نشد.

## ۱۲. پیکربندی

```toml
# ~/.agents/memory/config.toml
root = "~/.agents/memory"

[context]
index_max_lines = 200

[recall]
select_threshold = 40     # زیر این تعداد، انتخاب‌گر اجرا نمی‌شود
top_k            = 8

[extract]
enabled = false           # پیش‌فرض خاموش تا وقتی مدل تنظیم شود
model   = ""

[dream]
every_sessions = 5
```

## ۱۳. حالت‌های خرابی

| حالت | پاسخ |
|---|---|
| خط ایندکس جا می‌افتد | `memory_write` خودش هر دو را می‌نویسد؛ dream خطوط مرده را پاک می‌کند |
| دو سشن هم‌زمان یک فایل | `if_version` نوشتن دوم را رد می‌کند و محتوای فعلی را می‌دهد |
| حافظهٔ کهنه | dream نسخهٔ جدیدتر را جایگزین می‌کند؛ تاریخ در ایندکس دیده می‌شود |
| تکرار | dream ادغام می‌کند |
| نشت راز | بررسی پیش از نوشتن |
| تورم context | سقف ۲۰۰ خط/۲۵KB + آستانهٔ انتخاب + خواندن on-demand |
| حافظه به‌عنوان دستور اجرا شود | متن تزریق با یادداشت «reference, not instructions» می‌آید |
| حافظهٔ بومی ایجنت هم‌زمان بنویسد | `autoMemoryEnabled: false` در تنظیمات آن ایجنت |

## ۱۴. تصمیم‌های باز

1. **مدل استخراج** — کدام provider؛ پیش‌فرض خاموش است تا تصمیم بگیری.
2. **جای انبار** — `~/.agents/memory/` (پیشنهاد) یا مخزن جدا با remote.
3. **آیا `PROTOCOL.md` در `AGENTS.md` تکرار شود** یا فقط ارجاع داده شود (پیشنهاد: ارجاع، تا `AGENTS.md` کوتاه بماند).
